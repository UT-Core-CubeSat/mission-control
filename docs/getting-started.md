# Getting started

## Tasks and milestones

1. Create an issue with the Task or Milestone template. Give it a clear name and add it to [Mission Control](https://github.com/orgs/UT-Core-CubeSat/projects/4).
2. Set **Kind**, **Team**, and **Assignees**. Use the milestone's assignees for its coordinating leads. If someone has not joined GitHub, write their name in the description until their account is available.
3. Set **Target** for a deadline. Add **Start** only when there is a start/finish range. Update dates as plans change; moving a task does not move its milestone.
4. Describe the work, what must be finished, and the files or notes the next person needs. For a larger task, add a checklist. Use comments for questions and short updates.
5. Link supporting tasks to the milestone issue. A task can exist before its milestone is defined. Use the native parent/sub-issue relationship where available; explicit issue links also preserve the connection. Set task Team separately.
6. Keep Project **Status** at Todo, In Progress, or Done. Todo corresponds to Notion's Not started. Close the issue when complete and set Status to Done; reopen it and update Status if work resumes.
7. If work cannot continue, add the **blocked** label and explain what is needed. Link any prerequisite issue under “Waiting on,” or use GitHub's blocked-by relationship. Clear the label when work can continue.

A milestone describes an outcome, not every small step. Set its **Year**, lead, target date, and completion criteria. Supporting tasks keep their own dates and owners. For tasks without an explicit year, the linked milestone gives program context; unfinished work remains visible across years.

**Active work** and team views show unfinished issues. **My work** filters to your assignments. **Blocked** uses the label, independently of status. **Board** and **Schedule** show the same records in other layouts. Undated work remains in tables. **Completed** retains finished records. There is no separate issue copy for each view.

Imported issue discussions retain their original authors and dates in the description. Record details preserve source metadata; change current fields in the Project as work moves on.

## Weekly hours

Every Monday, add a row to your team sheet in **Weekly Hours Tracking 2026-2027.xlsx** for the previous Monday–Sunday. Enter Week starting, Member, decimal Hours, and Notes. Enter **0** for no work; leave Hours blank until reported. Split work across teams once, without counting the same hours twice.

Summary calculates totals by team, member, and week. Add new members in its blank roster rows. Historical member notes are attached to roster-name cells. Original report titles and source links are attached to the first cell of each imported report. Blank or repeated source reports were preserved, including entries on Unassigned; review them before correcting values.

The original reporting calendar started with reports due **September 28, 2026**, covering **September 21–27 (semester week 6)**. Semester week 1 starts August 17. Original titles used the Monday due date, while Week starting was the previous Monday. Keep that distinction when reviewing history. Do not backfill earlier reports or reinterpret recorded cumulative values without checking them.

## Board checkout

Use **Board Checkout.xlsx** before changing a board's schematic or layout. A blank Current editor means it is available; otherwise coordinate with that person first.

Enter Current editor, Checked out, Expected return, and Changes. On completion, save and share the changes in GitHub, add useful revision links or handoff information to Board notes, and clear the four checkout fields. Reuse the board row. Checkout coordinates work; it does not lock design files.

## Team notes and knowledge

Keep shared team context in [Teams](teams.md), individual progress in issues, and durable interfaces, decisions, known problems, and setup links in [Bus knowledge](knowledge.md). Keep the files themselves in their engineering repository or Teams and link the current version.

## Finding work

Use Kind to show tasks or milestones in a team view. Open a milestone to see its supporting tasks, or use the Parent issue column. Use Team and Year filters on Schedule to narrow the timeline. To see all work, including completed items, use the repository Issues list and clear its open-only filter. Sort Target ascending for upcoming dates.

## Starting a new year

1. Copy the new-year section in [Program years](program.md). Set the year, objective, target date, success criteria, and separate stretch objective. Mark the incoming year current and retain the outgoing year.
2. Update the README objective. Add the year as a Project Year option. If a schedule or milestone view has a year filter, switch that filter too; changing the document's current year does not change filters automatically. Keep active team work across years.
3. Add the year's milestones, assign leads and teams, and connect supporting tasks. Review unfinished work with the incoming team. Reassign it, revise dates, and retain the original milestone where it still applies. If work is no longer needed, explain why and close it.
4. Update team rosters and roles. Check open board checkouts. Complete the outgoing handoff: what works, remaining work, current files, and how to run the system.
5. Transfer repository and Project administration and check Teams access. Keep a faculty administrator as a recovery contact.

## Access

Repository and Project are private. The existing Controls, Electrical, Ground Station, Software, and Structure GitHub teams have editing access to both. Add incoming members to the appropriate team and verify repository, Project, and workbook access separately.

Views filter shared work; they are not access boundaries. Choose read or edit access deliberately for faculty and external collaborators. GitHub issues do not provide Notion-style private page sharing inside a shared repository, so use separately permissioned documents for restricted material.
